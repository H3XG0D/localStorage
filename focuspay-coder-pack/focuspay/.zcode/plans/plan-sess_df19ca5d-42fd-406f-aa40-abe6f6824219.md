### Цель
Довести V2-столы до полного безопасного цикла в личных сообщениях с ботом: 2–6 мест, 0–3 бота в UI, автоматический старт по заполнению, броски всех участников, переброс только лидеров при равенстве, неизменяемый итог и транзакционный расчёт на backend. До этого V2 в staging не выкладывается.

### Реализация
1. **Выделить V2 как отдельный игровой модуль**
   - Добавить `games/v2_table_gameplay.py`, не расширяя legacy `games/pvp.py`, который жёстко завязан на двух участников и `/games/*`.
   - Вынести чистые функции для roster по `seat_no`, правил количества бросков, приёма/валидации броска, подсчёта итогов, выявления лидеров и подготовки состояния переброса.
   - `seat_no`, а не Telegram ID, будет устойчивым ключом игровой логики; Telegram ID нужен только для проверки, что бросок прислал занимающий это место игрок.

2. **Долговечное игровое состояние V2**
   - Сохранять в `table.game_state` версионированный снимок: фаза, раунд, броски по местам, список лидеров tie-break и DM-соответствие запросов броска.
   - После каждого принятого броска сначала вызывать `persist-state` с `expected_state_version` и уникальным ключом идемпотентности; Telegram-интерфейс обновлять только из подтверждённого ответа backend.
   - На конфликте версии не применять бросок повторно вслепую: перезагрузить таблицу и заново показать актуальное состояние.

3. **Личные сообщения и ходы ботов**
   - При переходе стола в `running` отправлять каждому реальному участнику личный запрос с нужным emoji; индексировать ответ по `(Telegram ID, prompt message ID)` и сохранять этот ключ в `game_state` для восстановления после рестарта.
   - Проверять reply-to, emoji, участника и лимит бросков до любой записи в backend.
   - Для каждого bot-seat вызывать `send_dice` в служебном чате/DM-канале бота и пропускать полученное значение через те же V2-переходы, что и человеческий бросок. Боты будут равноправны в подсчёте и tie-break.

4. **Итог, tie-break и расчёт**
   - После заполнения нужных бросков подсчитать результаты всех мест.
   - При одном лидере: `commit-outcome(winner)` затем `settle-committed-outcome`; не использовать совместимый `/settle` с повторной передачей победителя.
   - При равенстве лидеров: `commit-outcome(tie_break)`; затем очистить только броски лидеров в новом раунде, сохранить состояние и отправить новые DM-запросы только этим участникам.
   - Итоговые уведомления о расчёте доставлять из V2 outbox, а не по локально рассчитанной сумме.

5. **Восстановление и фоновые задачи**
   - При старте и в отдельном цикле забирать V2 recovery snapshot/lease: восстанавливать DM-индексы, продолжать `outcome_committed` через `settle-committed-outcome`, а для running/tie-break повторно отправлять запрос только при отсутствии сохранённого актуального prompt.
   - Подтверждать recovery lease лишь после восстановления маршрутизации или безопасного продолжения расчёта.
   - Добавить V2 outbox-worker с claim/complete/fail и корректным retry; в тексте уведомления использовать только payload транзакционного settlement.
   - Добавить вызов V2 expiry для незапущенных столов по расписанию.

6. **Подключить пользовательский интерфейс V2**
   - В чистом staging-worktree подключить отдельный V2 мастер создания и кнопки «Активные игры» / «Мои игры» к `create_v2_table`, `send_v2_lobby` и `send_v2_my_tables`.
   - Сохранить только V2-ханки из загрязнённого `bot.py`; не включать карточки, пополнения, конфигурацию и другие чужие незакоммиченные изменения.
   - Поправить startup-тест: явно стаббировать V2-модуль и проверить регистрацию его обработчиков.

7. **Проверки**
   - Добавить unit-тесты: 3–6 мест, боты, неверный emoji/пользователь/ответ, повторный бросок, CAS-конфликт, 2- и 3-сторонний tie-break и восстановление маршрута после рестарта.
   - Расширить backend/staging E2E: создание с ботами, автозапуск финальным human join, V2 persist, tie-break → winner → commit → settle, bot-win, идемпотентный повтор, recovery lease и outbox retry.
   - Не запускать полный suite локально. После локальной статической/точечной проверки собрать две чистые локальные ревизии без push и выложить их только на `178.63.247.233` по `STAGING_RUNTIME.md`; там прогнать полный suite и V2 E2E.

### Граница работ
Production не затрагивается. Backend остаётся источником финансового решения: бот только валидирует Telegram-ввод и запрашивает V2 lifecycle API. Не потребуется изменять схему для первого этапа: DM-метаданные хранятся в `game_state`; при необходимости позже их можно нормализовать в отдельную миграцию.
