# Проверка работы ИИ по плану казино — инструкция для человека

Этот документ — для тебя, не для нейронки. Он отвечает на один вопрос: что нажать и посмотреть после каждого пункта плана, чтобы понять, сделано ли дело на самом деле.

**Разделение с 2026-08-28:** команды, git, тесты, md5, SQL, порты, метки прода — выполняет агент и присылает факты. Тебе остаётся только руками в интерфейсе: потыкать, сохранить, F5, сыграть раунд, сверить логику. Шелл-сокращения ниже — запасной контур, не обязательный ритуал каждого этапа.

Главный принцип по экрану: **не проверяй только по отчёту нейронки.** Отчёт в `docs/CASINO_WORKLOG.md` — оглавление. Доказательство по продукту — то, что ты видишь после клика.

## 1. Подготовка: настрой себе три сокращения

Один раз вставь это в шелл на staging, дальше все SQL-проверки станут однострочными.

```bash
ssh focuspay-test

cd /opt/focuspay/focussite

dc() { sudo docker compose --env-file /etc/focuspay/staging-runtime.env \
  -f docker-compose.staging-runtime.yml "$@"; }

psqlc() { dc exec -T postgres sh -c \
  "psql -U \"\$POSTGRES_USER\" -d \"\$POSTGRES_DB\" -tAc \"$1\""; }
```

Проверь, что работает:

```bash
dc ps
psqlc "SELECT count(*) FROM casino_settings;"
```

Интерфейс смотришь через туннель, с отдельного окна на своей машине:

```bash
ssh -N -L 18081:127.0.0.1:18081 focuspay-test
```

Дальше `http://127.0.0.1:18081/x8/casino` в браузере.

## 2. Сними эталоны один раз, до начала работ

Без этих трёх снимков половина проверок ниже теряет смысл — не с чем будет сравнить.

**Эталон 1. Прод не должен пошевелиться за всё время работ.** Запиши себе:

```bash
ssh focuspay 'stat -c "%y %n" /var/www/focuspay.org/index.html /var/www/focuspay.org/panel.html; systemctl show focuspay-exchange-api -p ActiveEnterTimestamp'
```

Три метки времени. После каждой задачи сверяешь — они обязаны остаться теми же. Это самая дешёвая и самая важная проверка во всём документе.

**Эталон 2. Как выглядят настройки казино сейчас.** Открой `http://127.0.0.1:18081/x8/casino/settings`, сделай скриншот всего экрана. И отдельно список ключей из базы:

```bash
psqlc "SELECT key FROM casino_settings ORDER BY key;"
```

Сохрани оба. Дальше по ним ловится классическая беда редизайна: экран стал красивее, а два поля с него пропали.

**Эталон 3. Базовая линия тестов.** Она уже снята и лежит в конце `docs/CASINO_WORKLOG.md`: 930 прошло, 7 упало, семь имён перечислены. Держи это число под рукой. Всё, что ниже 930 прошедших или больше семи упавших, — регрессия.

## 3. Универсальная проверка после каждой задачи

Одинаковая для всех восемнадцати задач, занимает минут пять. Делай её всегда, даже когда задача выглядит безобидной.

**Шаг 1. Прод цел.** Прогони команду из Эталона 1, сверь три метки времени. Разошлись — немедленно останавливай работу и разбирайся, это уже не про качество кода.

**Шаг 2. Объём изменений вменяемый.** У себя на машине:

```bash
cd ~/Desktop/focuspay && git status --short && git diff --stat
cd ~/Desktop/focuspay-casino && git status --short && git diff --stat
```

Смотри на список файлов, а не на код. Вопрос один: **относятся ли эти файлы к задаче?** Задача про реестр настроек, а в диффе тронут `CasinoDashboard.tsx` — почему? Спроси. Нейронки регулярно «заодно» правят соседнее, и именно это потом ломается неожиданно.

Второй вопрос — размер. Задача «добавить одну настройку» с диффом на полторы тысячи строк означает, что сделали не то, что просили.

**Шаг 3. Тесты прогоняешь ты, а не она.** На staging:

```bash
cd /opt/focuspay/focussite
sudo STAGING_RUNTIME_ENV_FILE=/etc/focuspay/staging-runtime.env ./scripts/staging-test.sh
```

Сравни с базовой линией. Правило простое: **новых имён в списке упавших быть не должно.** Не «примерно столько же», а именно ни одного нового имени. Если появилось — задача не принята, независимо от того, что написано в журнале.

Отдельно: если число прошедших выросло, а нейронка не говорила, что чинила чужие тесты, — тоже повод спросить. Иногда «починка» это удаление неудобной проверки.

**Шаг 4. Залито ли то, что ты смотришь.** Легко проверить одной строкой — сравни контрольную сумму любого тронутого файла:

```bash
# у себя
md5sum ~/Desktop/focuspay/site/exchange-backend/casino_finance.py
# на сервере
ssh focuspay-test 'md5sum /opt/focuspay/site/exchange-backend/casino_finance.py'
```

Суммы разные — значит, ты проверяешь на сервере старый код, и все остальные проверки этого круга недействительны.

**Шаг 5. Журнал заполнен по-человечески.** Открой свежую запись в `docs/CASINO_WORKLOG.md`. Плохая запись выглядит так: «тесты прошли», «всё работает», «healthcheck зелёный». Хорошая содержит числа и имена: сколько прошло, сколько упало, какие именно, какие файлы тронуты. Если чисел нет — требуй переписать, потому что следующий сеанс нейронки будет восстанавливаться именно отсюда, и на «всё работает» он восстановиться не сможет.

## 4. Главный класс ошибок: «сделано, но не подключено»

Если запоминать из этого документа только одно, запомни это. Самая частая и самая незаметная неудача ИИ — не сломанный код, а **код, который написан правильно и никем не вызывается.** Тесты зелёные, сборка чистая, в журнале рапорт, а функции нет.

Выглядит это так: настройка добавлена в реестр, но её никто не читает. Поле нарисовано на экране, но не попадает в запрос к серверу. Миграция написана, но не зарегистрирована и не выполняется. Эндпоинт создан, но фронт ходит на старый.

Проверяется в два счёта. Возьми имя того, что добавили, и посчитай, в скольких файлах оно встречается:

```bash
cd ~/Desktop/focuspay
rg -c "имя_новой_настройки" site/exchange-backend/ focussite/frontend/src/
```

Одно вхождение — объявили и забыли, это провал. Настройка должна встретиться минимум трижды: там, где объявлена, там, где применяется в расчёте, и там, где отдаётся в API.

Для интерфейса проверка ещё проще и надёжнее любого чтения кода: **измени значение в форме, сохрани, нажми F5.** Значение вернулось к старому — поле не подключено. Это ловит любые обрывы цепочки, на каком бы слое они ни были.

## 5. Признаки, что работу сдают формально

Не диагноз, а повод присмотреться.

**Тест, который не может упасть.** Открой новый тест и посмотри, что он утверждает. `assert result is not None` или проверка, что функция не бросила исключение, — это не тест. Тест должен сравнивать с конкретным ожидаемым числом. Для денежных задач (1, 2, 5, 6, 7) сделай контрольную проверку: закомментируй у себя строчку новой логики и прогони этот тест. Не упал — тест бесполезен, и зелёная сборка ничего не значит.

**Мокнуто всё подряд.** Если в тесте заглушены и база, и расчёт, и настройки, то он проверяет работу заглушек, а не твоей системы.

**Отчёт подробнее результата.** Три экрана описания сделанного при диффе в двадцать строк обычно означают, что описывали намерения, а не работу.

**Расширение задачи.** Просили реестр настроек, а заодно «улучшили» дашборд. Каждое такое «заодно» — непроверенное изменение в боевой логике казино.

**Тихая замена решения.** План говорит одно, сделано другое, в журнале об этом полстроки мелким шрифтом. Само по себе не грех, отклонения бывают полезными, но ты должен о них узнать до приёмки, а не через неделю.

## 6. Проверки по конкретным задачам

### Задача 0. Зафиксировать состояние — уже выполнена

Проверь: `docs/CASINO_WORKLOG.md` существует и содержит `git status` обоих репозиториев. Сверь HEAD из журнала с реальным:

```bash
cd ~/Desktop/focuspay && git log --oneline -3
cd ~/Desktop/focuspay-casino && git log --oneline -3
```

В журнале записаны два WIP-коммита — `a966162` в `focuspay` и `4b8d65e` в `focuspay-casino`. Убедись, что ты действительно давал на них разрешение, и что в них попала чужая незавершённая работа, а не что-то ещё.

Мелочь на подчистку: в `focuspay-casino` лежит мусорный файл с именем `=10.0.0` — это след от неудачной команды `pip install`. Его можно удалить.

### Задача 0Б. Канал в тестовую машину — уже выполнена

Тут проверять надо внимательнее обычного, потому что на этом канале держится всё остальное. Если он врёт, врать будут все последующие проверки.

**Заливка действительно доезжает.** Тронь у себя любой файл (например, допиши пустую строку в конец `README`), запусти `staging-sync.sh`, сверь `md5sum` с сервером. Совпало — канал живой.

**Оба дерева, а не одно.** Отдельно проверь второй репозиторий, про него легко забыть:

```bash
md5sum ~/Desktop/focuspay-casino/bot.py
ssh focuspay-test 'md5sum /opt/focuspay-casino/bot.py'
```

**Скрипт удаляет кое-что на сервере — посмотри, что именно.** В журнале записано, что `staging-sync.sh` перед синхронизацией сносит `/opt/focuspay/casino-client` и `/opt/focuspay-casino/.staging-e2e`. Открой скрипт и убедись, что список удаляемого именно такой и не расширяется:

```bash
rg -n "rm -rf|--delete" ~/Desktop/focuspay/focussite/scripts/staging-sync.sh
```

Любое `rm -rf` за пределами этих двух путей — вопрос к нейронке.

**Пароля в скриптах нет.**

```bash
rg -n "sshpass|PASSWORD|178\.63\.247\.233" ~/Desktop/focuspay/focussite/scripts/staging-sync.sh ~/Desktop/focuspay/focussite/scripts/staging-test.sh
```

IP как значение по умолчанию — нормально. Пароль в любом виде — нет.

**Портов наружу не прибавилось.** Тестовый сервис не должен ничего публиковать:

```bash
sudo docker ps --format 'table {{.Names}}\t{{.Ports}}'
```

Единственная строчка с публикацией — `127.0.0.1:18080` у gateway. Всё остальное — пусто.

**Исключение в регламенте описано честно.** Открой `focussite/STAGING_RUNTIME.md` и найди добавленный абзац. Он обязан разрешать прямую заливку **только для staging** и оставлять прод-правило нетронутым. Если формулировка размывает и продакшн — верни на переделку, это ровно тот случай, когда одна фраза в документе через месяц превращается в выкат на боевой сервер.

**Базовая линия снята поимённо.** В журнале семь конкретных имён упавших тестов, а не «7 failed». Имена есть — хорошо. Прогони тесты сам и убедись, что получаешь те же семь.

### Задача 1. Реестр настроек

Суть задачи — не добавить файл, а **убрать дублирование**. Поэтому главная проверка — что старые копии дефолтов исчезли:

```bash
cd ~/Desktop/focuspay
rg -n "DEFAULT_SETTINGS" site/exchange-backend/
```

Ожидаешь увидеть объявление в `casino_settings_registry.py` и импорты в остальных местах. Если в `routers/admin_casino.py` и `casino_finance.py` по-прежнему лежат свои словари с дефолтами — задача не сделана, как бы красиво ни выглядел новый файл.

Дальше: поведение не должно измениться ни на йоту. Открой `/x8/casino/settings` и сверь со скриншотом из Эталона 2. Все значения те же. И список ключей в базе не должен ни укоротиться, ни поменяться:

```bash
psqlc "SELECT key FROM casino_settings ORDER BY key;"
```

### Поправка после задачи 1. Отыгрыш = плюс казино, не «поставить 210»

Глоссарий плана говорил «оборот ставок». Подтверждённая модель: `wagering_percent` — сколько плюса казино должно получить комиссией с человека. При 21% и депозите 1000 ₽ это 210 ₽ комиссии, не ставка 210 ₽. Сколько поставить = 210 / комиссия «до отыгрыша». При 15% это 1400 ₽.

Кликни:

1. `http://127.0.0.1:18081/x8/casino/settings` — пример про 1000 ₽ должен говорить про 210 ₽ комиссии и 1400 ₽ ставок, не «отыграть ставками на 210».
2. В боте `/help`, «Пополнить» и профиль: тот же смысл (плюс казино + сколько поставить). Карточка профиля: поле «Нужно поставить».
3. Не начинай задачу 2, пока эта поправка не принята.

### Задача 2. Новые настройки

Проверь, что новые ключи реально доехали до интерфейса, а не только до кода. На экране настроек должны появиться новые поля.

Ключевое требование плана: **дефолты не меняют поведение**. Убедись глазами, что ограничители выключены:

```bash
psqlc "SELECT key, value FROM casino_settings WHERE key LIKE '%cap%' OR key LIKE '%floor%';"
```

Потолок комиссии и порог банкролла должны быть в нуле. Если нейронка проставила «разумные» ненулевые значения по своему усмотрению — это тихое изменение денежной логики, верни на исправление.

По каждой новой настройке прогони проверку из раздела 4: встречается ли имя больше одного раза.

### Задача 3. Миграция

Здесь спрятана ловушка, из-за которой миграция выполняется только на словах. Миграции на staging накатываются **по явному списку внутри скрипта**, а не по маске файлов. Проверь, что оба файла в списке:

```bash
rg -n "add_casino_settings_v2|volume_tier_grids" ~/Desktop/focuspay/focussite/docker/staging-db/00-apply-migrations.sh
```

Обе строки на месте — хорошо. Нет — миграция не выполнялась никогда, что бы ни утверждал журнал.

Теперь спроси у базы напрямую, а не у нейронки:

```bash
psqlc "SELECT key FROM casino_settings ORDER BY key;" | wc -l
psqlc "SELECT to_regclass('casino_cashback_volume_tiers');"
```

**Проверка идемпотентности, делай обязательно.** Она ловит самую опасную ошибку — миграцию, которая при каждом прогоне сбрасывает настройки в дефолт. Поменяй через интерфейс любое значение на заметное, например комиссию на 13 процентов. Запусти `staging-sync.sh` ещё раз (он перезапустит bootstrap и прогонит миграции заново). Открой настройки. **Твои 13 процентов обязаны остаться на месте.** Вернулось к дефолту — миграция написана через `DO UPDATE` вместо `DO NOTHING`, и в таком виде она однажды затрёт живые настройки.

### Задача 4. Аудит-лог

Проверяется руками за две минуты. Зайди в настройки, поменяй одно значение, укажи причину, сохрани. Затем:

```bash
psqlc "SELECT key, old_value, new_value, reason, changed_by FROM casino_settings_audit ORDER BY changed_at DESC LIMIT 5;"
```

Смотри на `old_value`: там должно быть **прежнее** значение, а не новое. Перепутанные местами старое и новое — типичная ошибка, и она полностью обесценивает аудит.

Второе: попробуй сохранить без причины. Форма обязана не дать. Третье: поменяй три настройки за одно сохранение — должно появиться три строки с одинаковым `batch_id`.

### Задача 5. Настройки в расчётах

Самая денежная задача, проверяй придирчиво.

Поставь потолок комиссии в маленькое число, сыграй крупный раунд через тестового бота и посмотри, что комиссия действительно упёрлась в потолок:

```bash
psqlc "SELECT game_id, amount, created_at FROM casino_commission_ledger ORDER BY created_at DESC LIMIT 5;"
```

Отдельно — про снимок цены. Требование плана: настройка, влияющая на цену раунда, попадает в `pricing_snapshot`, иначе изменение настройки задним числом перепишет расчёт уже сыгранных партий. Проверь, что снимок содержит новые поля:

```bash
psqlc "SELECT game_data->'pricing_snapshot' FROM casino_games ORDER BY id DESC LIMIT 1;"
```

И сделай контрольную проверку теста из раздела 5: закомментируй строку, применяющую потолок, прогони тест на потолок. Он обязан упасть.

### Задача 6. Карточные игры на сервере

Смысл задачи — убрать генерацию исхода из бота. Значит, в боте её быть не должно:

```bash
cd ~/Desktop/focuspay-casino
rg -n "SystemRandom|random\.shuffle|shuffle\(" games/baccara.py games/blackjack.py
```

Пусто — сделано. Осталась хоть одна тасовка на стороне бота — не сделано, вне зависимости от того, что появилось на бэкенде.

Проверь, что до готовности игры выключены:

```bash
psqlc "SELECT value FROM casino_settings WHERE key = 'enabled_games';"
```

Потом сыграй партию в баккару на staging и убедись, что она вообще идёт.

### Задача 7. Provably fair

Позитивная проверка простая: сыграй раунд, возьми хеш и сид, прогони через эндпоинт проверки, получи подтверждение.

**Негативная проверка важнее, и её легко забыть.** Возьми тот же сид и испорти в нём один символ. Проверка обязана сказать «не сходится». Если и на испорченном сиде она отвечает «всё честно» — верификатор всегда возвращает успех, то есть его нет. Это выглядит работающим ровно до первого спора с игроком.

В PvP отдельно: оба игрока должны видеть один и тот же хеш до начала раунда.

### Задача 8. Примитивы интерфейса

Низкий риск. `npm run build` чистый, экраны не развалились. Подробно смотреть смысла нет, эти компоненты проверятся сами собой в задачах 9–13.

### Задача 9. Экран настроек

Здесь главный риск — потерянные поля. Достань скриншот из Эталона 2 и **пересчитай поля**. Ещё надёжнее — сравни с реальным списком ключей:

```bash
psqlc "SELECT key FROM casino_settings ORDER BY key;"
```

Каждый ключ, который редактировался раньше, обязан редактироваться и сейчас. Пропавшее поле означает настройку, которую больше нельзя изменить из интерфейса, и заметишь ты это в худший момент.

Дальше — проверка из раздела 4: поменяй значение, сохрани, обнови страницу. Значение осталось — цепочка цела.

И проверь, что форма требует причину изменения, раз уж в задаче 4 это заявлено обязательным.

### Задача 10. Сетки тиров

Введи сетку с намеренным разрывом — например, один тир кончается на 100 тысячах, следующий начинается со 150 тысяч. Валидация обязана возразить. Не возразила — сетка сможет молча не начислять кэшбэк тем, кто попал в дыру.

Сохрани нормальную сетку, обнови страницу, проверь, что значения на месте.

### Задача 11. Риск-дашборд

Дашборд опасен тем, что красиво врёт. Возьми **одно** число с экрана и проверь его запросом к базе. Например, оборот за неделю:

```bash
psqlc "SELECT sum(bet_amount) FROM casino_games WHERE created_at > now() - interval '7 days';"
```

Сошлось — можно верить остальному. Не сошлось — дашборд декоративный.

### Задача 12. Экран аудита

Поменяй настройку, зайди на экран аудита, найди своё изменение. Проверь, что показывается именно «было — стало», а не только «стало».

### Задача 13. Чек-лист готовности

Чек-лист обязан отражать реальное состояние сервера, а не мнение фронтенда. Проверка простая: **сломай что-нибудь нарочно.** Выключи робота дома или обнули его баланс. Соответствующий пункт обязан покраснеть. Остался зелёным — чек-лист рисует картинку, а не проверяет.

### Задача 14. Дизайн-токены

Посмотри на палитру. Она не должна повторять тёмно-синий с ярко-зелёным, как у Stake — это не вопрос вкуса, а вопрос узнаваемого чужого оформления. Структуру токенов копировать можно, конкретные цвета — нет.

### Задачи 15–17. Игровой интерфейс

Через туннель пройди путь игрока целиком: лобби, выбор игры, ставка, результат. Проверь арифметику руками — при ставке 100 и коэффициенте 2 в поле выигрыша должно стоять 200 минус комиссия, и это должно совпасть с тем, что реально пришло на баланс.

Проверь границы: ставка ниже минимума и выше максимума обязаны отбиваться, причём с внятным текстом, а не молча.

Открой на телефоне через тот же туннель — верстка не должна разъезжаться.

### Задача 18. Telegram Mini App

Открой в тестовом боте. Тема должна подхватываться из Telegram, а не быть прибитой гвоздями. Проверь и светлую, и тёмную. Нижняя кнопка — родная телеграмовская. Прокрутка не должна дёргаться.

## 7. Если проверка не прошла

Не чини сам и не проси «просто поправить». Полезнее сделать три вещи.

Скажи нейронке **конкретно, что ты увидел**, без интерпретации: какую команду запустил, что ожидал, что получил. «Поменял комиссию на 13, перезапустил sync, стало 5» работает намного лучше, чем «миграция кривая».

Потребуй **не переходить к следующей задаче**, пока эта не закрыта. План построен последовательно, и наслоение исправлений поверх непринятой задачи — то, из-за чего такие работы обычно и разваливаются.

Проверь, что **исправление попало в журнал**. Если запись осталась прежней и рапортует об успехе, следующий сеанс нейронки прочитает её и продолжит с ложной картины мира.

Отдельный случай — если разошлись метки времени прода. Тут не разбирайся сам: останови работу и посмотри, что именно изменилось на боевом сервере, прежде чем продолжать что бы то ни было.
