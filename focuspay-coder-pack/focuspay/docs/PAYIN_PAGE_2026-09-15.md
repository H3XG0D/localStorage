# Приём средств — 2026-09-15

## Реализация

`/ops/payout-requisites`: приём по умолчанию; выплаты с карты во вторичной вкладке. Ручные реквизиты и реквизиты SELL используют прежние API и права. Форма открывается кнопкой; созданный payin ждёт включения. Максимум платежей 1–5, крипта/стоимость/срок в дополнительных настройках.

Карточка показывает цель, получено, ожидается, свободно, источник, ответственного и платежи. Проверка открывает справа получателя, клиента, статистику и чек. Отклонение явно отменяет заявку; снятие/закрытие предупреждает об освобождении резервов. Прогноз свёрнут и помечен приблизительным.

Общий список и только выбранная деталь обновляются через 8 секунд после завершения предыдущего опроса, а также после действий. Выбор хранится по ID; устаревшая деталь не используется после переключения. Ошибка обновления блокирует подтверждение и действия по реквизиту. Конфликт/ошибка операции инициирует обновление. Неполные статистические поля отображаются как «—».

Нет изменений бэкенда, бота, финансовых формул, выдачи прав или миграций. Доступ к чужим деталям ограничен сервером. Счётчик проверки относится к доступным платежам. Архив ограничен текущим API (до 100 записей), подпись указывает ограничение.

## Ограничение выпуска

Staging не обновлён. Read-only SSH к `focuspay-test` успешен, но `git -C /opt/focuspay status` возвращает `not a git repository`. STAGING_RUNTIME.md требует утверждённый SHA и чистый checkout, а текущая локальная папка содержит многочисленные изменения других задач. Исключение прямой синхронизации в runbook касается плана казино.

Для выпуска нужно согласовать отдельный способ доставки этой сборки либо подготовить утверждённый коммит и восстановить процесс checkout на staging. Прод не затронут.

Полный интеграционный цикл SELL/ручного реквизита, реальное PDF-превью и конкурентные запросы двух операторов на staging остаются обязательными перед выпуском. Изолированный UI smoke и юнит-тесты не доказывают транзакционную безопасность живой БД.
