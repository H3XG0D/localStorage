# Исправление логики распределения

Важное правило, согласованное для реализации:

## Ручная заявка

Если клиентский оператор лично общался с клиентом, выдал реквизиты, проверил оплату и передал заявку на выплату, то клиентская часть операторского фонда принадлежит только этому оператору.

Она не делится между всеми клиентскими операторами на смене и не зависит от того, сколько других операторов видели заявку.

```text
client_pool_rub → intake_operator_id
```

Финансовая часть делится между финансовыми участниками, реально назначенными на выплату. TX hash вводит только финансовый оператор, имеющий доступ к кошельку.

## Автоматическая заявка

Если заявка автоматически проверена ботом и не была проведена конкретным клиентским оператором:

- клиентская часть делится между всеми назначенными клиентскими участниками;
- финансовая часть делится между всеми назначенными финансовыми участниками;
- при отсутствии индивидуальных весов доли равные;
- количество участников не увеличивает общий фонд — оно только делит уже рассчитанный пул;
- отсутствие участников роли фиксируется явно как нераспределённая сумма по политике администратора.

Пример: операторский фонд заявки 300 ₽, из него 120 ₽ клиентский пул и 180 ₽ финансовый пул.

```text
Автоматическая заявка:
2 клиентских оператора → по 60 ₽
1 финансовый оператор → 180 ₽
```

Для ручной заявки в тех же условиях:

```text
1 клиентский оператор, работавший с клиентом → 120 ₽
второй клиентский оператор → 0 ₽
1 финансовый оператор → 180 ₽
```

## Защита выплаты

- только `finance` может принять заявку в финансовую работу;
- только назначенный финансовый оператор может видеть поле TX hash;
- только он может вызвать подтверждение выплаты;
- backend дополнительно проверяет роль, назначение, статус, уникальность TX и идемпотентность;
- клиентский оператор не может подменить TX hash через frontend, Telegram или прямой API вызов.


### 2.2. Настройки администратора

Администратор задаёт два независимых параметра:

```text
operator_pool_percent — процент чистой прибыли, который направляется в зарплатный фонд
client_operator_share_percent — доля фонда клиентским операторам
finance_operator_share_percent — доля фонда финансовому оператору
```

Ограничения backend:

```text
0 <= operator_pool_percent <= 100
0 <= client_operator_share_percent <= 100
0 <= finance_operator_share_percent <= 100
client_operator_share_percent + finance_operator_share_percent = 100
```

Настройки должны иметь версию и дату начала действия. Для каждой завершённой заявки сохранять snapshot настроек, применённых к расчёту. Изменение настроек администратором не должно пересчитывать старые заявки.

### 2.3. Пример

Чистая прибыль заявки:

```text
1 000 ₽
```

Администратор установил:

```text
30% чистой прибыли → зарплатный фонд
70% чистой прибыли → остаётся владельцу/бизнесу
```

Тогда фонд операторов:

```text
1 000 × 30% = 300 ₽
```

Администратор дополнительно установил:

```text
40% фонда → клиентские операторы
60% фонда → финансовые операторы
```

Распределение заявки:

```text
Клиентский пул: 300 × 40% = 120 ₽
Финансовый пул: 300 × 60% = 180 ₽
```

Если на заявке один клиентский оператор и один финансовый оператор:

```text
Клиентский оператор получает 120 ₽
Финансовый оператор получает 180 ₽
```

Если на заявке два клиентских оператора:

```text
Клиентский пул 120 ₽ распределяется между двумя участниками
по зафиксированным правилам участия, а не начисляется дважды.
```

### 2.4. Распределение между участниками заявки

Нельзя умножать фонд на количество операторов. Сначала рассчитываются два пула заявки:

```text
client_pool_rub  = operator_pool_rub × client_operator_share_percent
finance_pool_rub = operator_pool_rub × finance_operator_share_percent
```

Затем каждый пул распределяется по участникам соответствующей роли. Для распределения сохраняется список участников с весами:

```text
client_participants:
  - operator_id: 11, weight: 100
  - operator_id: 12, weight: 0

finance_participants:
  - operator_id: 21, weight: 100
```

Сумма весов внутри каждой роли должна быть ровно 100% для той роли, которая участвует в распределении.

#### Ручная заявка

Ручная заявка — это заявка, в которой клиентский оператор реально общался с клиентом, выдал реквизиты, проверил оплату и передал заявку на выплату.

Правило:

- `client_pool_rub` получает **только тот клиентский оператор, который сопровождал эту заявку** (`intake_operator_id`);
- другие клиентские операторы не получают клиентскую долю этой заявки, даже если они были на смене, видели заявку или помогали в очереди;
- `finance_pool_rub` распределяется между финансовыми участниками заявки по их зафиксированным весам;
- если финансовый оператор один, он получает 100% финансового пула;
- если финансовых операторов несколько, их веса должны быть назначены явно и в сумме давать 100%.

Пример: два клиентских оператора и один финансовый оператор:

```text
Клиентский оператор A — общался с клиентом и передал заявку → 100% client_pool
Клиентский оператор B — не является участником начисления → 0 ₽
Финансовый оператор F — выполнил выплату → 100% finance_pool
```

#### Автоматическая заявка

Автоматическая заявка — заявка, проверенная ботом/системой без клиентского сопровождения конкретным клиентским оператором.

Правило:

- `client_pool_rub` распределяется между **всеми назначенными клиентскими участниками** автоматической заявки;
- `finance_pool_rub` распределяется между **всеми назначенными финансовыми участниками** автоматической заявки;
- распределение выполняется по равным или явно заданным весам;
- если участники одной роли назначены без индивидуальных весов, backend использует равные доли;
- если участников роли нет, её пул не распределяется молча: сумма записывается отдельной строкой `unassigned_client_pool_rub` или `unassigned_finance_pool_rub` по политике администратора.

Пример автоматической заявки с двумя клиентскими и одним финансовым оператором:

```text
client_pool = 120 ₽
finance_pool = 180 ₽

Клиентский оператор A → 60 ₽ (50% client_pool)
Клиентский оператор B → 60 ₽ (50% client_pool)
Финансовый оператор F → 180 ₽ (100% finance_pool)
```

Если автоматическую заявку одновременно выполнили два финансовых оператора с равными весами:

```text
Каждый получает 50% finance_pool.
```

Это правило относится только к автоматическим заявкам. Для ручной заявки клиентская доля никогда не делится между всеми клиентскими операторами смены — она принадлежит конкретному оператору, который работал с клиентом.

Изменения состава участников после завершения выплаты запрещены обычным операторам и доступны только администратору через отдельную корректировку с аудитом.

## 3. Роли и права

### 3.1. Клиентский оператор

Разрешено:

- искать клиента;
- создавать ручную заявку;
- принимать заявку на клиентское сопровождение;
- передавать заявку в финансовую очередь;
- видеть статус, комментарии и назначенного финансового оператора;
- запрашивать уточнение у клиента;
- видеть свои начисления и историю.

Запрещено:

- видеть рабочие кошельки и приватные финансовые реквизиты;
- принимать финансовую заявку;
- вводить TX hash;
- подтверждать выплату;
- менять финансового оператора;
- повторно подтверждать уже выплаченную заявку.

### 3.2. Финансовый оператор

Разрешено:

- видеть финансовую очередь;
- принимать заявку на выплату;
- видеть необходимые реквизиты выплаты;
- выполнять выплату из доступного кошелька;
- единолично вводить TX hash;
- подтверждать выплату после backend-проверок;
- вернуть заявку на уточнение с причиной;
- видеть свои начисления.

Запрещено:

- создавать начисления вручную;
- менять формулу прибыли;
- менять процент зарплатного фонда;
- назначать участников заявки;
- подтверждать выплату без TX hash и проверок backend.

### 3.3. Администратор

Разрешено:

- назначать роль оператору;
- менять роль оператора;
- включать/отключать оператора;
- менять настройки фонда и распределения;
- назначать/переназначать участников заявки;
- делать корректировку начисления только отдельной audit-операцией;
- видеть полный журнал назначений и расчётов.

## 4. Изменения модели данных

### 4.1. Роль в `operator_accounts`

Добавить:

```text
operator_role            -- client | finance
role_changed_at
role_changed_by
```

Роль применяется к новым действиям. Уже назначенные заявки не должны теряться при смене роли.

### 4.2. Участники заявки

Старое `orders.operator_id` сохранить для обратной совместимости. Для нового процесса добавить явные поля или нормализованную таблицу.

Рекомендуемый вариант — таблица `order_operator_participants`:

```text
id
order_id
operator_id
role                     -- client | finance
participation_type       -- intake | payout | helper
share_weight_percent     -- вес внутри роли
assigned_by              -- operator/admin id или системный источник
assigned_at
released_at
created_at
```

В заявке также сохранить удобные текущие ссылки:

```text
intake_operator_id       -- основной клиентский оператор, nullable
finance_operator_id      -- принявший финансовый оператор, nullable
paid_by_operator_id      -- фактически подтвердивший выплату
```

`paid_by_operator_id` использовать как фактического исполнителя выплаты, а не как замену финансовому назначению.

### 4.3. Источник заявки

Добавить/нормализовать:

```text
order_source              -- manual_client_operator | telegram_auto | web | other
verification_source       -- operator | telegram_bot | merchant | other
```

Эти поля нужны для очереди, Telegram-уведомлений и правил автоматических заявок.

### 4.4. Версия финансовых настроек

Таблица `operator_payroll_settings`:

```text
id
operator_pool_percent
client_operator_share_percent
finance_operator_share_percent
auto_unassigned_policy   -- business | finance_pool
valid_from
valid_to
created_by
created_at
```

Выплата/начисление заявки хранит snapshot:

```text
payroll_settings_id
net_profit_rub
operator_pool_rub
client_pool_rub
finance_pool_rub
unassigned_client_pool_rub
```

### 4.5. Распределение и идемпотентность

Таблица `order_payroll_splits`:

```text
id
order_id
payroll_settings_id
net_profit_rub
operator_pool_rub
client_pool_rub
finance_pool_rub
status                 -- pending | accrued | corrected
created_at
accrued_at
```

Таблица/строки участников распределения:

```text
order_payroll_split_lines
split_id
operator_id
role
weight_percent
amount_rub
ledger_entry_id
created_at
```

Ограничения:

- уникальный split на одну заявку и один финальный payout event;
- уникальный ledger entry на `(split_id, operator_id, role)`;
- начисление в транзакции вместе с финализацией выплаты;
- повторный callback бота или повторный POST не создаёт второе начисление;
- округление выполнять на backend, остаток копеек отдавать финансовой доле или явно записывать как rounding adjustment.

### 4.6. Уровень оператора и коэффициент участия

Роль доступа и уровень оплаты — разные измерения:

```text
role:  client | finance       -- какие действия доступны
grade: trainee | junior | senior -- коэффициент участия внутри роли
```

Для оператора с двумя ролями профиль уровня хранится отдельно для каждой роли
(`operator_id`, `role`, `grade`, `weight_multiplier`). Начальные коэффициенты можно
задать как `0.75 / 1.00 / 1.25`, но администратор должен иметь возможность изменить
их в настройках зарплаты без изменения ролей доступа.

Расчёт внутри пула выполняется по весам, а не по индивидуальному проценту:

```text
operator_amount = role_pool_rub × operator_weight / sum(role_weights)
```

Для ручной заявки клиентский пул получает только `intake_operator_id`. Для
автоматической заявки пул делится между явно назначенными участниками роли.
В админской панели нужны два уровня настроек: доля `client/finance` в общем фонде
и таблица коэффициентов `trainee/junior/senior`. В операторской панели нужен
read-only индикатор текущего распределения по роли и список фактических участников
с их весом; значения должны приходить из backend snapshot конкретной смены/заявки.

## 5. Жизненный цикл ручной заявки

### 5.1. Создание клиентским оператором

```text
intake_operator_id = текущий client operator
order_source = manual_client_operator
status = OPERATOR_PENDING
finance_operator_id = NULL
```

Заявка появляется в очереди финансовых операторов.

### 5.2. Claim финансовым оператором

Использовать атомарную операцию:

```sql
UPDATE orders
SET finance_operator_id = $operator_id,
    finance_claimed_at = now()
WHERE order_id = $order_id
  AND finance_operator_id IS NULL
  AND status IN ('OPERATOR_PENDING', 'COMPLETED')
RETURNING *;
```

Если вернулась пустая строка:

```text
Заявка уже принята другим финансовым оператором
```

Два финансовых оператора не могут получить одну заявку.

### 5.3. Выплата

Только финансовый оператор с `finance_operator_id = current_operator_id` видит поле TX hash и кнопку подтверждения.

Backend при подтверждении:

1. проверяет роль `finance`;
2. проверяет, что заявка закреплена за этим оператором;
3. проверяет статус;
4. проверяет TX hash через существующий bot bridge;
5. проверяет уникальность TX hash;
6. записывает `paid_by_operator_id`;
7. переводит заявку в `PAID`;
8. в одной транзакции создаёт payroll split и ledger lines;
9. после commit отправляет уведомления.

При ошибке уведомления выплата не откатывается и не повторяется: событие уведомления должно быть outbox/idempotent.

### 5.4. Запрос уточнения

Финансовый оператор может вернуть заявку с причиной:

```text
needs_clarification = true
clarification_reason
```

Клиентский оператор получает задачу уточнить данные. TX hash на этом этапе отсутствует.

## 6. Жизненный цикл автоматической заявки

1. Telegram-бот или backend фиксирует автоматическую проверку.
2. Заявка получает `order_source = telegram_auto`.
3. Заявка попадает сразу в финансовую очередь.
4. `intake_operator_id = NULL`.
5. Финансовый оператор делает claim.
6. Только он вводит TX hash.
7. После успешной выплаты backend применяет политику `auto_unassigned_policy`.

Бот не рассчитывает прибыль, проценты или зарплату. Он только передаёт событие и уведомляет о результате backend.

## 7. Интерфейс администратора

### 7.1. Карточка оператора

Поля:

```text
Логин
Имя
Роль: Клиентский / Финансовый
Активен
На смене
Заявок в работе
Начислено
Выплачено
```

Изменение роли требует подтверждения:

> Новая роль применяется к новым действиям. Уже назначенные заявки останутся за текущими участниками.

### 7.2. Настройки зарплаты

Отдельный блок:

```text
В зарплатный фонд: [30] % чистой прибыли
Клиентские операторы: [40] % фонда
Финансовые операторы: [60] % фонда
Автоматическая заявка без client operator: [финансовый пул / бизнес]
```

Предпросмотр для прибыли 1 000 ₽:

```text
Чистая прибыль                 1 000 ₽
В фонд операторов (30%)          300 ₽
Клиентский пул (40% фонда)       120 ₽
Финансовый пул (60% фонда)       180 ₽
```

Нельзя сохранить настройки, если доли не дают 100%.

### 7.3. Управление участниками заявки

Администратор видит:

```text
Клиентский оператор: Иван · 100%
Финансовый оператор: Алексей · 100%
```

При двух клиентских операторах администратор должен явно указать веса, например:

```text
Иван       70%
Мария      30%
```

Без весов второй оператор остаётся наблюдателем и не получает начисление. Автоматическое удвоение начисления запрещено.

## 8. Интерфейс клиентского оператора

Разделы:

```text
Смена
Новая заявка
Мои заявки
Передано на выплату
Нужно уточнение
История начислений
```

После передачи заявки отображать:

```text
Передано финансовому оператору
Финансовый оператор: Алексей
TX hash вводит финансовый оператор
```

Поле TX hash и кнопка подтверждения отсутствуют в клиентской роли.

## 9. Интерфейс финансового оператора

Разделы:

```text
К выплате
Автоматически проверенные
Мои выплаты
На уточнении
История выплат
Начисления
```

В карточке:

```text
Источник заявки
Клиентский оператор
Сумма
Криптовалюта и сеть
Кошелёк/реквизиты
Проверки backend
```

Действия:

```text
Принять выплату
Запросить уточнение
Ввести TX hash
Подтвердить выплату
```

Только после claim и только у финансового оператора показываются TX input и кнопка подтверждения.

```text
Финансовый оператор: ...
Статус: выплата в работе
```

### Выплата завершена

```text
✅ Заявка #...
Выплата подтверждена
Финансовый оператор: ...
TX: ...
```

### Payroll

Подробные суммы 30/70 отправлять только в закрытый payroll-топик, администратору и соответствующим операторам. В общем рабочем чате зарплату не показывать.

Telegram callback не должен сам менять статус напрямую без backend-проверок и идемпотентного ключа.

## 11. API и проверки доступа

Новые/изменяемые endpoint-ы:

```text
PATCH /api/admin/operators/{id}/role
GET   /api/admin/operator-payroll/settings
PUT   /api/admin/operator-payroll/settings
GET   /api/admin/operator-payroll/splits

GET   /api/operator/queue?role=client
GET   /api/operator/queue?role=finance
POST  /api/operator/orders/{id}/claim-intake
POST  /api/operator/orders/{id}/claim-finance
POST  /api/operator/orders/{id}/request-clarification
POST  /api/operator/orders/{id}/release-finance
POST  /api/operator/orders/{id}/payout
GET   /api/operator/payroll
```

Старые endpoint-ы не удалять сразу. На переходном этапе:

- старый `operator_id` продолжает работать для старых заявок;
- `/claim` проверяет роль и перенаправляет в role-specific логику;
- старое подтверждение payout разрешено только финансовому оператору;
- миграция старых заявок выполняется без изменения уже созданных ledger-записей.

## 12. Тестовые сценарии

Тестировать локально/на тестовой базе, без реальных выплат:

1. Админ создаёт настройки `30% фонда`, `40/60`.
2. Preview показывает при чистой прибыли 1 000 ₽ фонд 300 ₽.
3. Клиентский оператор создаёт ручную заявку.
4. Финансовый оператор видит заявку.
5. Клиентский оператор не видит TX input.
6. Клиентский оператор не может вызвать payout endpoint.
7. Два финансовых оператора одновременно делают claim — проходит только один.
8. Один финансовый оператор вводит TX hash и подтверждает выплату.
9. Повторный POST с тем же idempotency key не создаёт второе начисление.
10. Повторный Telegram callback не создаёт вторую выплату.
11. Два клиентских оператора не получают двойной фонд.
12. При двух участниках с весами 70/30 сумма начислений равна клиентскому пулу.
13. Автоматическая заявка без client operator корректно обрабатывает выбранную политику.
14. Смена роли не теряет уже назначенную заявку.
15. Старые заявки и старые ledger-записи отображаются без пересчёта.
16. TX hash другого оператора отклоняется.
17. Дублирующий TX hash отклоняется.
18. Сбой Telegram после commit не откатывает выплату и не создаёт повтор при retry.
19. Недоступность bot bridge блокирует подтверждение, но не создаёт частичную выплату.
20. Админская корректировка создаёт отдельную audit-запись.

Запрещено использовать production для тестов:

- реальный payout;
- реальное подтверждение TX;
- отмена живой заявки;
- изменение реальных начислений;
- принудительное закрытие рабочей смены.

## 13. Порядок реализации

### Фаза 0 — согласование

Утвердить:

- процент фонда от чистой прибыли;
- долю client/finance внутри фонда;
- правило автоматической заявки без клиентского оператора;
- правило нескольких участников и их весов;
- доступ к payroll-суммам в Telegram;
- разрешение/запрет двойной роли одному человеку.

### Фаза 1 — backend foundation

- миграция ролей;
- permission matrix;
- таблицы участников и audit;
- настройки с версиями;
- snapshot финансовых правил;
- совместимость со старым `operator_id`.

### Фаза 2 — безопасная очередь

- отдельные client/finance очереди;
- атомарный claim;
- release/clarification;
- role-based endpoint guards;
- TX only for finance role.

### Фаза 3 — payroll split

- расчёт фонда от существующей чистой прибыли;
- распределение по настройкам администратора;
- split lines и ledger;
- идемпотентность;
- обработка нескольких операторов;
- автоматические заявки.

### Фаза 4 — интерфейс

### Фаза 5 — Telegram

- топики;

- закрытые payroll-уведомления;

### Фаза 6 — rollout

1. Локальный backup.
2. Миграции на тестовой базе.
3. Unit и transaction integration tests.
4. Сборка frontend/backend.
5. Read-only smoke.

10. Проверка очереди и ledger.
11. Постепенное включение остальных операторов.

## 14. Критерии готовности

- Клиентский оператор может провести заявку до финансовой очереди без доступа к кошельку и TX.
- Финансовый оператор единственный может ввести TX hash и подтвердить выплату.
- Два финансовых оператора не могут одновременно завладеть одной заявкой.
- Два клиентских оператора не создают двойное начисление.
- Сумма всех split lines равна операторскому фонду с учётом явно записанного округления/неиспользованной доли.
- Изменение настроек применяется только к новым завершённым заявкам.
- Повторные POST/webhook/callback идемпотентны.
- Старые заявки, выплаты и ledger не ломаются и не пересчитываются задним числом.
- Полная цепочка назначения, выплаты и начисления восстанавливается из audit log.
