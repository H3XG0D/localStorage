# FocusVPN — Архитектура

> **Статус:** PHASE 1 — архитектурный blueprint. Документ не содержит implementation code.
> Основан на проверенном `docs/OPEN_SOURCE.md` (верифицировано 10.08.2026).
> Дата: 10.08.2026.

---

## 1. Назначение и область

Документ фиксирует целевую архитектуру VPN-сервиса **FocusVPN**: закрытый коммерческий клиент
для 5 платформ, собственный control plane, собственная VPN-инфраструктура (node), три VPN-движка.
Цель blueprint'а — дать точную схему, по которой дальше будет писаться код (PHASE 2+).

### 1.1 Цели (non-goals на PHASE 1)

- Не проектируем собственный VPN-протокол и собственную криптографию.
- Не используем fork AmneziaVPN client как основу клиента (GPL-3.0) — только пермиссивные движки.
- Не создаём микросервисы ради микросервисов — **modular monolith**.
- Не проектируем billing/платёжных провайдеров (только каркас подписок).
- Не проектируем Kubernetes и оркестрацию на PHASE 1.
- Не пишем код.

## 2. Высокоуровневая схема

```
                          +---------------------------------------------------+
                          |              CONTROL PLANE (backend)               |
                          |   modular monolith · Go · PostgreSQL · Redis      |
                          |   REST API (user/admin/agent) · mTLS с нодами     |
                          +-----+-----------------------------------+---------+
                                | TLS/HTTPS (клиенты)   | mTLS (node agent)
                                v                       v
        +------+------+--------+----------+      +-----------------------------+
        | Android/iOS | Windows/macOS/Linux |      |        VPN NODE            |
        |  клиенты     |  клиенты            |      |  Node Agent (Go)          |
        |  +VPNEngine  |  +VPNEngine         |      |   ├── amneziawg           |
        +-------------+---------------------+      |   ├── wireguard           |
              клиент сам выбирает движок            |   └── xray (VLESS+REALITY)|
              и тянет конфигурацию через API        +-----------------------------+
                          ^                                   ^
                          +------------ VPN tunnel -----------+
                            (AmneziaWG / WireGuard / VLESS+REALITY)
```

Поток материалов:

1. **Control Plane** — источник правды: пользователи, устройства, подписки, ноды, эндпоинты,
   аллокации, шаблоны конфигураций. Никогда не хранит приватный ключ клиента.
2. **Node Agent** — автономный агент на каждой ноде: принимает «желаемое состояние» от CP,
   применяет его к локальным VPN-движкам, отдаёт телеметрию/здоровье обратно.
3. **Клиент** — генерирует собственные ключи на устройстве, получает от CP «части конфигурации»
   (публичные ключи сервера, IP, DNS, эндпоинт), собирает конфиг локально и поднимает туннель
   через абстракцию `VPNEngine` (AmneziaWG / WireGuard / Xray).

## 3. Принципы (вывод из OPEN_SOURCE.md)

| Принцип | Решение |
|---|---|
| Встраиваем в закрытый клиент только permissive/MPL | amneziawg-go (MIT), wireguard-go (MIT), Xray-core/amnezia-xray-core (MPL-2.0), amnezia-libxray (MIT), wintun.dll (Prebuilt Binaries License) |
| GPL-компоненты — только как отдельные процессы на нодах | `awg` (GPL-2.0), `wg`/`wg-quick` (GPL-2.0), kernel-модуль — не линкуем, не правим |
| MPL-файлы не правим | Xray конфигурируем только через JSON |
| Базы клиентов | wireguard-android (Apache-2.0), wireguard-apple (MIT) — пермиссивные форки |
| Никакой собственной криптографии | только алгоритмы, реализованные в движках |
| Фиксируем версии движков, ведём NOTICE/THIRD_PARTY_LICENSES | требование сторов и аудита |

**Технические замечания к принятой стратегии (фиксируем явно, ничего не скрываем):**

1. **Xray/VLESS+REALITY** — единственный из трёх движков, где узел обязан знать **идентификатор
   клиента (VLESS UUID)** для аутентификации. Это не приватный ключ WG, но это креденциал;
   CP вынужден его видеть/хранить. Смягчение: UUID — per-device, шифруется at rest (envelope),
   передаётся на ноду только по mTLS, ротация по отзыву устройства. Это фундаментальное свойство
   протокола, обойти «backend не видит ничего» для VLESS нельзя.
2. **wintun.dll** — бинарник распространяем только «рядом с ПО», через публичный API
   (`LoadLibraryEx` + динамический вызов), не модифицируем и не редистрибутим сам по себе.
3. **MPL-2.0** Xray означает: если мы правим файлы Xray/amnezia-xray-core, эти файлы обязаны
   быть открыты под MPL. Стратегия — не править ядро вовсе (только JSON-конфиги).

## 4. Control Plane — modular monolith

Один Go-процесс (`backend`), один деплой, одно Postgres-подключение. Внутри — логические
модули с чёткими границами. Домены НЕ выносятся в микросервисы без реальной необходимости
(масштаб и стоимость поддержки на PHASE 1 этого не оправдывают). Горизонтальное масштабирование
— несколько реплик одного процесса за L7-балансировщиком, Postgres и Redis остаются внешними.

### 4.1 Модули и их ответственность

| Модуль | Ответственность | Не делает |
|---|---|---|
| **auth** | Регистрация, вход/выход, refresh token rotation, выпуск access-токенов, защита от brute force, смена пароля | Не хранит сессии в Postgres (refresh — в Redis/hash в Postgres) |
| **users** | Профиль, статус аккаунта, RBAC-роль, блокировка/удаление, запросы `/v1/me`, `/v1/subscription` | Не знает про VPN-протоколы |
| **devices** | Модель устройств, регистрация, выдача device token, ключи (public key WG/AmneziaWG), отзыв, замена, ротация ключей, лимит устройств по плану | Не хранит приватные ключи |
| **subscriptions** | Планы, подписки, сроки, лимиты (max_devices), статусы active/expired/trialing | Billing/платежи — задел, в MVP заглушка |
| **nodes** | Каталог VPN-нод, состояние (HEALTHY/DEGRADED/DRAINING/OFFLINE), mTLS-сертификаты агентов, регистрация нод | Не применяет конфиги на ноды (это Node Agent) |
| **endpoints** | Эндпоинты нод (протокол, порт, публичный ключ сервера, параметры обфускации, REALITY-параметры), состояние, метрики | — |
| **allocations** | Выделение VPN-IP клиенту на эндпоинте, жизненный цикл аллокации (active→revoked), связка device↔endpoint | — |
| **configurations** | Сборка и подпись «частей конфигурации» клиента, версионирование, ротация, отзыв, шифрование at rest | Никогда не содержит приватный ключ клиента |
| **health** | Приём heartbeat от клиентов и агентов, расчёт метрик (latency, packet loss, load), переходы состояний нод/эндпоинтов | — |
| **scheduler** | Фоновые задачи: чистка просроченных токенов/аллокаций/телеметрии, плановые ротации ключей, повторные проверки здоровья, подписки | — |
| **admin** | Admin REST API, RBAC-проверки, аудит админских действий | — |
| **platform/** | Общие инфраструктурные подсистемы: http/роутинг, middleware (auth, rate limit, request id, logging), postgres (pgx), redis, конфиг, секреты | — |

### 4.2 Связи между модулями (правила)

- Модули общаются через **внутренние Go-интерфейсы/порты**, а не через HTTP между собой.
- Все запросы к данным — только через репозиторий модуля (никаких «чужих» таблиц напрямую).
- Транзакционные сценарии (например, «аллокация + публикация peer на ноде») идут через сервис
  оркестратора (`allocations` вызывает порт `nodes` → постановка задания агенту), с компенсацией
  при сбое: аллокация помечается `pending`, при неудаче → `failed`/откат.
- Redis используется для: rate limiting, кэш NodeSelector, pub/sub «конфиг изменился → агент
  переполлил», краткосрочные счётчики, глобальные замки.

### 4.3 Технологический стек CP (финально)

- **Go** (последний стабильный), один бинарь `backend/cmd/server`.
- **PostgreSQL 16** — единственная система хранения правды.
- **Redis 7** — вспомогательный слой (кэш, rate limit, pub/sub, замки).
- **REST API** (JSON), JWT access + opaque refresh rotation + opaque device token.
- **Docker** для сборки/локальной разработки. Без Kubernetes на PHASE 1.
- Миграции БД — версионированные SQL (см. DATABASE.md). ORM не используем (pgx + sqlc).

## 5. Data Plane — VPN-нода и Node Agent

### 5.1 Что находится на VPN-ноде

Одна Linux-нода (`DE-01`) содержит:

- **Node Agent** — Go-демон, единственный «умный» процесс на ноде.
- **Системные VPN-инструменты** как отдельные процессы (не линкуются):
  - `awg` (amneziawg-tools, GPL-2.0) для настройки интерфейса AmneziaWG;
  - `wg`/`wg-quick` (wireguard-tools, GPL-2.0) для WireGuard;
  - `xray` (Xray-core / amnezia-xray-core, MPL-2.0) для VLESS+REALITY;
  - опционально `amneziawg-linux-kernel-module` (GPL-2.0, часть ядра) для максимальной скорости.
- **Несколько VPN-эндпоинтов** — один и тот же узел может поднимать несколько протоколов/портов:

```
DE-01
 ├── amneziawg   (UDP :51820, obfuscation Jc/Jmin/Jmax)
 ├── wireguard   (UDP :51821, чистый WireGuard)
 └── reality     (TCP :443, VLESS + REALITY, SNI-маскировка)
```

### 5.2 Что делает Node Agent

- **Бутстрап/регистрация**: однократно вызывает CP с одноразовым node-token → получает `node_id`
  и mTLS-сертификат (CSR-флоу, собственный внутренний CA).
- **Получение желаемого состояния**: long-poll `GET /v1/agent/state?since=<version>`
  (таймаут **30 s**, re-poll **≤5 s**); CP через Redis pub/sub форсирует немедленный wake
  после изменений (см. ADR-004, DECISIONS.md).
- **Применение состояния**: транслирует «желаемое состояние» в команды движкам:
  - добавление/удаление peer в AmneziaWG через subprocess **`awg`** (MVP);
  - генерация/обновление Xray JSON-конфига (Phase 4), перезапуск xray при изменении;
  - настройка интерфейса: listen port, MTU, DNS, параметры обфускации (Jc/Jmin/Jmax, уникально на ноду).
- **Телеметрия/здоровье**: каждые ~15–30 с шлёт CPU/load, per-endpoint rx/tx, peer_count,
  status движков, error-коды. CP считает по этим данным состояния.
- **Управление ключами сервера**: генерация серверных x25519-ключей (WG/AmneziaWG) и REALITY-ключей
  Xray; приватный ключ сервера живёт только на ноде; публичный передаётся CP для конфигов клиентов.
- **Ключ ротации**: по расписанию CP (или сам агент) ротирует серверные ключи; старая конфигурация
  остаётся валидной короткое окно перехода.

### 5.3 Данные между CP и Node Agent

**Агент → CP:**
- node/endpoint heartbeat и метрики здоровья (load, rx/tx, peer_count, packet loss, ошибки движков);
- подтверждение применения состояния (applied version);
- регистрация/обновление эндпоинтов (публичные ключи, реальные порты, конфиг REALITY — без приватных ключей);
- событие ротации серверных ключей (новый публичный ключ).

**CP → Агент:**
- желаемое состояние: список peers (device public key + IP + quota-флаги), параметры интерфейсов,
  параметры обфускации AmneziaWG, Xray inbound-конфиг (список UUID, REALITY-настройки);
- команды отзыва (revoke peer), отмены активных соединений на DRAINING-ноде;
- указание на ротацию ключей сервера.

### 5.4 Аутентификация CP ↔ Node Agent

- **mTLS** по выделенному порту/пути; каждый агент имеет клиентский сертификат от внутреннего CA.
- Сертификаты короткоживущие (≈90 дней), автопродление через CSR-флоу; отзыв — через CRL/список
  отозванных в CP, проверяемый при handshake.
- Нода идентифицируется по `node_id` из сертификата (CN/SAN), а не по IP.
- TLS-версии и cipher-наборы — по внутренней политике (см. SECURITY.md).

### 5.5 Provisioning / revocation / rotation

**Provisioning (новый клиент на ноде):**
1. Клиент регистрирует устройство → присылает только **публичный** ключ.
2. CP создаёт allocation: выбирает эндпоинт (NodeSelector), выдаёт VPN-IP из подсети эндпоинта.
3. CP публикует «желаемое состояние» для ноды (peer = pubkey + IP).
4. Агент применяет (wg/awg set / xray users) → подтверждает версию состояния.
5. CP помечает allocation `active`, собирает конфиг для клиента.
6. Клиент собирает конфиг локально (вставляет свой приватный ключ) и поднимает туннель.

**Revocation (отзыв устройства/конфига):**
1. CP переводит allocation/device в `revoked`, инкрементирует версию конфигурации.
2. CP публикует агенту команду удаления peer / UUID → агент применяет.
3. Повторный fetch конфига возвращает 410 Gone; cached-конфиг клиента помечается невалидным
   по подписи/версии при следующем обращении к CP.

**Rotation (ротация ключей):**
- **Клиентские ключи** — по требованию (или подозрении на компрометацию): клиент генерирует новую
  пару локально, шлёт новый публичный ключ; CP обновляет allocation и peer на всех эндпоинтах
  устройства (стандартный WG-флоу: старый ключ заменяется).
- **Серверные ключи** — планово (напр., раз в 90 дней): агент генерирует новую пару, публикует новый
  публичный ключ в CP; CP выпускает новые конфиги; окно перекрытия (старый ключ валиден 24 ч)
  исключает обрыв активных сессий.
- **mTLS-сертификаты агентов** — автопродление (см. 5.4).

## 6. User flow

### 6.1 Основной поток нового пользователя

```
register → login → tokens → регистрация device → список servers
        → POST /connections (NodeSelector выбирает endpoint)
        → GET /configurations/:id (части конфига, БЕЗ приватного ключа)
        → клиент собирает конфиг локально → establish VPN tunnel
        → periodic heartbeat/telemetry → disconnect → reconnect
```

Шаг за шагом:
1. `POST /v1/auth/register` — email + пароль (Argon2id). Ответ: профиль + access/refresh.
2. `POST /v1/auth/login` → access (JWT, ~15 мин) + refresh (opaque, rotation).
3. `POST /v1/devices` — клиент генерирует на устройстве ключевую пару (приватная остаётся в
   Keychain/Keystore/secure storage), передаёт `public_key` + имя/платформу/версию приложения.
   Ответ: `device_id` + **device token** (выдаётся один раз, хранится на CP только хэш).
4. `GET /v1/servers` — список доступных эндпоинтов по подписке и предпочтениям протокола.
5. `POST /v1/connections` — CP запускает NodeSelector, выдаёт VPN-IP, публикует состояние агенту,
   возвращает упорядоченный **candidate list** эндпоинтов (для failover) + `config_id`.
6. `GET /v1/configurations/:id` — клиент получает подписанные части конфига: IP/DNS/mtu, публичный
   ключ сервера, endpoint host/port, параметры обфускации (AmneziaWG) или REALITY-параметры (Xray).
7. Клиент локально собирает полный конфиг (вставляет приватный ключ), вызывает `VPNEngine.start()`,
   поднимает туннель.
8. `POST /v1/heartbeat` — минимальная телеметрия (см. §11). Туннель держится, пока не выключим.
9. `DELETE /v1/connections/:id` (disconnect) — CP отмечает активную сессию закрытой; туннель
   рвётся на клиенте. Повторное подключение — шаги 5–7 (конфиг может быть переиспользован из кэша
   до истечения TTL).

### 6.2 Краевые сценарии

| Сценарий | Поведение |
|---|---|
| **Первый запуск** | Регистрация account → регистрация device (генерация ключей) → выбор региона → подключение |
| **Повторный запуск** | Клиент логинится (refresh), берёт кэшированные конфиги/кандидатов; если TTL конфига истёк — `POST /v1/connections` заново. Туннель поднимается без лишних запросов, если конфиг ещё валиден |
| **Истёкшая подписка** | CP при `GET /v1/servers`/`/v1/connections` возвращает 402 Payment Required (или 403), клиент показывает экран «подписка истекла», туннель не поднимается; существующие аллокации деактивируются |
| **Удалённое устройство** | При следующем heartbeat/запросе — 401/410 (device revoked); конфиги устройства отозваны, peers сняты с нод |
| **Отключённый node / недоступный endpoint** | `DELETE /v1/connections/:id` + перевыбор: клиент пробует следующий кандидата из списка (failover, §10); при исчерпании — свежий `POST /v1/connections` |
| **Backend недоступен** | Клиент использует кэшированные конфиги и известные эндпоинты напрямую; туннель не рвётся, если уже поднят; при недоступности всех — корректное сообщение, без infinite retry |

## 7. Device model

Один пользователь → несколько устройств:

```
User
 ├── iPhone      (iOS)
 ├── MacBook     (macOS)
 ├── Windows PC  (Windows)
 └── Android     (Android)
```

- **Device identity**: `device_id` (UUID), создаётся при регистрации устройства; неизменяемый.
- **Ключи**: каждый клиент генерирует пару x25519 (WG/AmneziaWG) локально; **приватный ключ никогда
  не покидает устройство** (хранится в iOS Keychain / Android Keystore / DPAPI / libsecret).
  На CP и на нодах — только публичные ключи.
- **Device token**: opaque случайный токен (32 байта), выдаётся один раз при регистрации, на CP
  хранится только хэш (SHA-256/BLAKE2b). Используется для device-scoped запросов
  (`/v1/configurations/:id`, `/v1/heartbeat`).
- **Отзыв устройства**: `DELETE /v1/devices/:id` → device_token_hash обнуляется, все allocations
  переходят в `revoked`, ноды получают команду удаления peers. Принудительно — по лимиту устройств
  или по запросу пользователя.
- **Лимит устройств**: задаётся планом (напр., Free=1, Pro=5, Business=10). При превышении — отказ
  регистрации с кодом, предлагающим отозвать старое устройство.
- **Замена устройства**: новый device регистрируется как обычно; старый отзывается пользователем
  (или по лимиту). VPN-ключи новые — старые peers снимаются с нод.
- **Ротация ключей устройства**: `POST /v1/devices/:id/rotate-key` — клиент генерирует новую пару,
  шлёт новый публичный ключ; CP обновляет allocation и peers на всех активных эндпоинтах.

## 8. VPN configuration — безопасный lifecycle

### 8.1 Модель «частей» (композиция на клиенте)

Ключевое решение: **backend никогда не получает и не хранит приватный ключ клиента.**

| Материал | Где генерируется | Где хранится | Кто видит |
|---|---|---|---|
| Приватный ключ клиента (WG/AmneziaWG) | на устройстве | secure storage устройства | только клиент |
| Публичный ключ клиента | на устройстве | CP + ноды (peer) | CP, нода |
| Приватный ключ сервера (WG/AmneziaWG) | на ноде (Node Agent) | нода | только нода |
| Публичный ключ сервера | на ноде | CP + конфиги клиентов | CP, клиент |
| Приватный REALITY-ключ Xray | на ноде | нода (xray config) | только нода |
| VLESS UUID (креденциал клиента для Xray) | на устройстве* | secure storage устройства + нода (users) + CP (шифр. копия) | CP (encrypted), нода |

\*UUID можно генерировать и на клиенте (анонимизированнее), но нода обязана знать его для
аутентификации VLESS — это ограничение протокола (см. §3, замечание 1).

### 8.2 Жизненный цикл

1. **Генерация keypair** — на устройстве при регистрации/ротации.
2. **Хранение приватного ключа** — в secure storage устройства, изолировано от кода уровня приложения.
3. **Что отправляется в backend** — только публичный ключ (WG) / UUID (Xray, шифруется at rest).
4. **Что отправляется на ноду** — публичный ключ клиента + IP (peer), UUID (Xray users); по mTLS.
5. **Что получает клиент** — подписанные части: server public key, endpoint host/port, IP/DNS/MTU,
   параметры обфускации, REALITY-параметры. **Приватного ключа нет нигде в ответе.**
6. **Отзыв** — см. §5.5: status→revoked, версия инкремент, peers сняты, fetch→410.
7. **Обновление** — версии конфигураций: клиент видит новую подпись/версию при следующем обращении.
8. **Смена эндпоинта** — клиент меняет только `endpoint`-часть (server public key может остаться тем
   же, если тот же узел/интерфейс); конфиг пересобирается локально, приватный ключ не переиздаётся.

### 8.3 Целостность и подпись

- CP подписывает части конфигурации ключом Ed25519 (`config_signing_key`); клиент проверяет подпись.
- Каждая часть имеет `config_version`; отзыв/ротация всегда увеличивает версию.
- Конфигурация в БД хранится зашифрованной (envelope encryption, см. SECURITY.md).

## 9. Node selection

```
NodeSelector
    ↓
фильтрация кандидатов (состояние, страна/регион, протокол, лимиты)
    ↓
Scoring (взвешенная сумма нормализованных показателей)
    ↓
упорядоченный candidate list → Best endpoint (первый в списке)
```

### 9.1 Фильтрация кандидатов

Кандидат `(node, endpoint)` допускается, только если:
- `node.state == HEALTHY` и `endpoint.state == HEALTHY` (не DEGRADED/DRAINING/OFFLINE);
- страна/регион соответствуют запросу (или включён «fastest»);
- протокол доступен: `amneziawg` (по умолчанию), `wireguard`, `reality` — по подписке/настройкам;
- остаточная ёмкость > порога (например, load < 0.8 или peer_count < capacity*0.9).

### 9.2 Scoring (концептуальная формула)

Для кандидата `e` и пользователя `u`:

```
score(e) = w_health · H(e)
         + w_cap    · C(e)
         - w_load   · L(e)
         - w_lat    · lat(e)/lat_max
         - w_loss   · PL(e)
         + w_geo    · G(u,e)
         + w_proto  · P(u,e)
```

Где:
- `H(e)` — здоровье эндпоинта: 1.0 для HEALTHY, плавное затухание с ростом ошибок/сбоев;
- `C(e)` — доля свободной ёмкости `1 − load`;
- `L(e)` — нормализованная загрузка (CPU/память/пропускная способность);
- `lat(e)` — оценочная задержка (агрегат клиентских проб + гео-эвристика; в Redis c TTL);
- `PL(e)` — packet loss (0..1), штраф суперлинейный;
- `G(u,e)` — гео-аффинити: 1.0 если страна совпадает с выбором пользователя, 0.5 — регион, иначе
  убывание по расстоянию (или 0 для явного выбора страны);
- `P(u,e)` — бонус приоритета протокола (по умолчанию AmneziaWG выше за счёт анти-DPI устойчивости);
- веса `w_*` нормализованы в сумме = 1, настраиваются конфигом.

Ответ клиенту — **весь упорядоченный список** (top-N, напр. 3), чтобы failover шёл без новых запросов.

## 10. Failover и reconnect

### 10.1 Состояния нод и эндпоинтов

```
HEALTHY → DEGRADED → DRAINING → OFFLINE
```

- **HEALTHY** — метрики в норме, принимает новые аллокации.
- **DEGRADED** — нагрузка > 85% ИЛИ packet loss 5–20% ИЛИ пропущено 2 heartbeat подряд.
  Новые аллокации ещё допускаются с пониженным скорингом.
- **DRAINING** — новые аллокации запрещены (NodeSelector исключает); активные сессии
  дорабатывают до естественного завершения; после этого — `OFFLINE`/maintenance.
- **OFFLINE** — недоступен, heartbeat пропущен (N раз), исключён из выбора.

Переходы: HEALTHY⇄DEGRADED — автоматически (health-модуль); DRAINING — администратором
(обслуживание) или автоматически при критических метриках; OFFLINE — автоматически.

### 10.2 Что происходит при сбоях

| Событие | Реакция |
|---|---|
| **Node умер** | Health-модуль переводит в OFFLINE; NodeSelector исключает; клиенты на его эндпоинтах получают разрыв → failover на следующих кандидатов |
| **Endpoint умер** (один из трёх) | Endpoint → OFFLINE; остальные эндпоинты ноды работают; клиенты конкретного протокола переходят на другие |
| **Node перегружен** | DEGRADED → пониженный скор; при критическом — DRAINING |
| **Высокий packet loss** | Endpoint/Node → DEGRADED/DRAINING; клиент по порогу потерь инициирует failover сам |
| **Backend недоступен** | Клиент работает на кэшированных конфигах; новые выборы невозможны, но работающий туннель не рвётся |
| **VPN-туннель разорвался** | Клиентский reconnect с exponential backoff (ниже) |

### 10.3 Reconnect strategy (без бесконечного цикла)

Клиент работает со списком кандидатов, полученным при `POST /v1/connections`:

1. При разрыве — пробуем следующий эндпоинт из списка **без обращений к backend**.
2. Между попытками — **exponential backoff + jitter**:
   `delay = min(cap, base · 2^n + rand(0, jitter))`, `base = 1s`, `cap = 30s`, `jitter = base`.
3. После N попыток по всем кандидатам (например, 2 полных прохода) — **свежий запрос**
   `POST /v1/connections` за новым списком.
4. Общий лимит сессии: после K неудач (например, 10 попыток) — остановка с понятным пользователю
   состоянием «retrying…», **без фонового бесконечного лупа**; повтор — по действию пользователя.
5. При успехе — сброс счётчиков backoff к нулю.

## 11. Privacy и телеметрия

**Мы не строим систему хранения истории посещений.** Никогда не собираем и не храним:
- browsing history, DNS history, содержимое трафика, имена хостов/доменов назначения.

Туннель «немой» на уровне CP/нод: CP не видит трафик, ноды видят только шифрованные пакеты.

### 11.1 Минимальная телеметрия (белый список)

| Поле | Источник | Зачем |
|---|---|---|
| `app_version` | клиент | поддержка, анализ версий |
| `platform` | клиент | поддержка |
| `node` / `endpoint` | клиент/агент | выбор узлов, SLA |
| `connection_state` | клиент | диагностика соединений |
| `latency`, `packet_loss` | клиент | качество, NodeSelector |
| `error_code` | клиент/агент | диагностика, деградация |

### 11.2 Хранение

- **Аггрегированные метрики** (обезличенные, по нодам/регионам) — до **30 дней**, затем удаление.
- **Сырые события** (персональные, с device/user) — до **24 ч** для диагностики, затем delete.
- События пишутся в отдельную таблицу/стор и чистятся планировщиком (`scheduler`).
- Никаких связей «какие сайты открывал пользователь X» в данных не существует принципиально.

## 14. Риски (Phase 1 → Phase 2)

| Риск | Влияние | Митигация |
|---|---|---|
| Userspace AmneziaWG на ноде медленнее kernel | throughput при росте peers | Kernel-модуль как опциональный рантайм (не в продукте); мониторинг load [ADR-002] |
| Задержка poll CP↔agent | peer появляется с лагом после connect | Long-poll + Redis wake; дефолты в DECISIONS.md; `409 stale_version` → full re-sync [ADR-004] |
| Случайная GPL-зависимость в клиенте | блок стора / раскрытие кода | CI license gate; NOTICE + THIRD_PARTY_LICENSES; только permissive в бинарнике |
| Секреты без KMS на старте | утечка ключей подписи/KEK | Dev: file-backed KEK; prod: Secret Manager до открытия админки |
| Дрейф 5 клиентских кодовых баз | рассинхрон ConfigParts | `clients/shared/` контракты с Phase 2 (CLI) и Phase 3 |
| ASN/subnet blocking эндпоинтов | массовый outage региона | Задел Phase 4: пул IP, быстрая смена endpoint (не MVP) |
| AWG 1.x fingerprint vs DPI 2026 | блокировки в жёстких сетях | MVP: Jc/Jmin/Jmax + уникальные params на ноду; оценка AWG 2.0 (H/S/I) — отдельное решение при пинe версии |

## 15. Резюме PHASE 1

Phase 1 зафиксировал blueprint коммерческого FocusVPN без кода:

- Control Plane — Go modular monolith + Postgres + Redis [ADR-001].
- Data plane — Node Agent (mTLS + desired-state poll) [ADR-004]; движки permissive [ADR-002].
- Клиенты — собственные на wireguard-android / wireguard-apple + desktop; не форк Amnezia client [ADR-003].
- Конфиги — Ed25519-подпись, без приватного ключа клиента на CP [ADR-005].
- Сессии — JWT access + rotating refresh [ADR-006].
- MVP — одна нода AmneziaWG, без billing/multi-node/REALITY ([ROADMAP.md](ROADMAP.md) §1).

**Следующий шаг:** утверждение blueprint → Phase 2 (backend + agent + CLI harness). Детали DoD — ROADMAP §3.
