# Phase 2 · Milestone 3 — Design

> **Status:** IMPLEMENTED (11.08.2026). See [[CURRENT_TASK]] / [[DECISIONS]].
> Sources: [[ARCHITECTURE]], [[API]], [[DATABASE]], [[SECURITY]], [[005-configuration-security]], [[004-node-agent]], [[ROADMAP]], [[CURRENT_TASK]], [[DECISIONS]].

## 1. Goal and DoD

Implement the Control Plane half of the vertical slice after auth/devices (M1–M2):

| Deliverable | Notes |
|---|---|
| `GET /v1/servers` | List selectable endpoints (MVP: DE-01 AmneziaWG) |
| `POST/DELETE /v1/connections` | Create/revoke allocations + return `config_id` |
| `GET /v1/configurations/:id` | Signed ConfigParts; auth via `X-Device-Token` |
| Envelope encryption at rest | AES-256-GCM + file-backed KEK (`FOCUSVPN_KEK_PATH`) |
| Ed25519 ConfigParts signing | Distinct `config_signing_key` (≠ JWT key) |
| Migration `000002` | Tables `vpn_allocations`, `vpn_configurations` |

**Out of M3 (explicit):**

- Node-agent apply / mTLS / long-poll / `awg` — **M4**
- CLI connect/disconnect + real tunnel E2E — **M5**
- REALITY / Xray / multi-node failover scoring — Phase 4
- Prod KMS/HSM — pre-prod (SECURITY §11.2)

## 2. Scope boundary vs M4

Ideal ARCHITECTURE flow waits for agent confirm before `active`. Seeded DE-01 historically was `OFFLINE` with `public_key` NULL. **Approved A1:** seed DEV-ONLY server public key + HEALTHY for local/dev; auto-`active` only on a dev-scoped path; M4 restores agent confirm.

Until M4:

- “Publish desired state to agent” may be an in-process no-op / log + DB version bump (no Redis pub/sub required in M3).
- Peer removal on DELETE is recorded in DB; agent apply is M4.

## 4. API contracts

Contracts already sketched in [[API]] §5–§7. M3 locks the following.

### 4.1 `GET /v1/servers`

- Auth: access JWT.
- Query: optional `country`, `protocol` (MVP: ignore multi-country; filter protocol if set).
- Response: `{ "endpoints": [{ "id", "node", "country", "region", "protocol", "score" }] }`.
- MVP NodeSelector stub: return the single HEALTHY AmneziaWG endpoint (DE-01) with a fixed score (e.g. `1.0`). No multi-candidate ranking until Phase 4.
- Errors: `invalid_token`, `expired_token`, `subscription_expired` (402) — see §17 Open Decision C on free-plan fallback.

### 4.2 `POST /v1/connections`

- Auth: access JWT.
- Body: `{ "device_id", "protocol", "country?", "region?" }`.
- Preconditions: device owned by caller and `active`; subscription gate per §17-C; endpoint selectable (HEALTHY AmneziaWG for MVP).
- Behavior:
  1. Resolve device; snapshot `peer_public_key`.
  2. Select endpoint (stub).
  3. In one transaction: allocate IP → insert allocation `pending` → build ConfigParts → envelope-encrypt → Ed25519-sign → insert `vpn_configurations` version=1 `active`.
  4. Transition allocation per §17-A (stub active vs stay pending).
  5. Return `201` with `connection.id` (= allocation id), status, candidates (single), `config_id`, `config_version`.
- Errors: `device_not_found`, `node_unavailable` (503), `subscription_expired` (402), `too_many_allocations` (409) — limit TBD §17-B, `forbidden`, `validation_error`.

### 4.3 `DELETE /v1/connections/:id`

- Auth: access JWT; owner only (or admin later).
- Behavior: mark allocation `revoked` (+ `revoked_at`); mark related configs `revoked`; bump version lineage so subsequent GET → `410 Gone`; free IP for reuse (unique partial indexes release pending/active constraint). Peer-removal command is desired-state for M4 — **always intended**, not optional (clarifies vague API “при желании”).
- Response: `204`.
- Errors: `not_found`, `forbidden`.

### 4.4 `GET /v1/configurations/:id`

- Auth: **`X-Device-Token`** (opaque device token), **not** access JWT.
- Device must own the configuration; config must be `active` (else `410` if revoked; `404` if unknown).
- Response shape per API §7 (parts + `config_version` + `signature` base64). Never returns client private key, DEK, KEK, or envelope internals.
- Client must verify signature and reject `config_version < cached` (client-side; CP still serves current active version).

## 5. Allocation lifecycle

```
        ┌──────────┐
        │ pending  │──fail──► failed
        └────┬─────┘
             │ agent confirm / M3 stub
             ▼
        ┌──────────┐
        │  active  │──revoke──► revoked
        └──────────┘
```

| From | To | Trigger |
|---|---|---|
| (new) | `pending` | `POST /connections` creates row |
| `pending` | `active` | Agent applied desired state (M4) **or** approved M3 stub |
| `pending` | `failed` | Unrecoverable provisioning failure |
| `active` | `revoked` | DELETE connection, device revoke, subscription expiry job |
| `failed` / `revoked` | — | Terminal (new connection = new allocation row) |

**Ownership:** `user_id` (denormalized), `device_id`, `endpoint_id`, `peer_public_key` snapshot, `ip`.

**Constraints (DATABASE §2.7):**

- `UNIQUE(endpoint_id, ip) WHERE status IN ('pending','active')`
- `UNIQUE(device_id, endpoint_id) WHERE status='active'`

**Idempotency (proposed):** If the same user/`device_id`/`protocol` already has a `pending` or `active` allocation on the selected endpoint, return that connection + current `config_id`/`config_version` instead of creating a duplicate (HTTP 200 or 201 — pick one at implementation; prefer **200** for reuse, **201** for create). Document in DECISIONS when implementing.

**Concurrency:** IP allocation inside a transaction; rely on partial unique indexes; on unique_violation retry with next free IP (bounded retries). Optional `pg_advisory_xact_lock` on `endpoint_id` for clearer serialization (same pattern as device-limit lock in M2).

**Transaction boundary:** allocation insert + first configuration insert (encrypt+sign outside or inside tx after crypto) must commit together; if crypto fails, roll back allocation.

## 6. IPAM (MVP)

- Subnet from endpoint: seed `10.200.0.0/24`.
- Reserve network address and broadcast; reserve gateway/DNS host **`.1`** (`10.200.0.1`) per API examples.
- Allocate next free host IP not present in pending/active rows for that endpoint.
- Interface address in ConfigParts: `"<ip>/32"`.
- DNS: `["10.200.0.1"]`; MTU: `1420` (MVP constants; not yet columns on `vpn_endpoints` — document as CP constants until schema needs them).

## 7. ConfigParts structure

Plaintext object (never includes client private key):

```json
{
  "interface": {
    "address": "10.200.0.10/32",
    "dns": ["10.200.0.1"],
    "mtu": 1420
  },
  "peer": {
    "server_public_key": "<std-base64 x25519>",
    "endpoint": "de-01.focusvpn.example:51820",
    "allowed_ips": ["0.0.0.0/0", "::/0"]
  },
  "protocol": {
    "name": "amneziawg",
    "obfuscation": {
      "junk_packet_count": 4,
      "junk_min_size": 40,
      "junk_max_size": 70
    }
  },
  "xray": null
}
```

Obfuscation values for DE-01 are **locked** (Jc=4, Jmin=40, Jmax=70) from seed / API §7. Unique per node policy unchanged.

## 8. Cryptography

Primitives only from approved stack: **Ed25519**, **AES-256-GCM**, **SHA-256**, file-backed KEK. No new algorithms. Libs: Go stdlib `crypto/ed25519`, `crypto/aes`, `crypto/cipher`, `crypto/sha256`, `crypto/rand`; existing `golang.org/x/crypto` already in module (argon2) — no new dependency required for M3 crypto.

### 8.1 What is signed

Ed25519 signature over the **canonical signing payload** bytes:

```json
{"config_version":<int>,"parts":<ConfigParts>}
```

### 8.2 Canonical representation

Proposed rules (confirm §17-D):

1. UTF-8 JSON.
2. Object keys sorted lexicographically at every object level (including nested).
3. No insignificant whitespace (compact encoding).
4. Arrays keep documented order (`dns`, `allowed_ips`).
5. Numbers as JSON numbers (no quotes); `null` for `xray` in MVP.
6. Strings as JSON strings; `server_public_key` is std base64 of 32 raw bytes.

Wire field `signature` = **standard Base64** of the 64-byte Ed25519 signature (matches API.md wording).

### 8.3 What is encrypted at rest

AES-256-GCM ciphertext of the **canonical ConfigParts JSON only** (the `parts` object bytes under the same canonical rules as above, **without** wrapping `config_version` — version lives in DB column + signing payload). Client private keys are never present.

### 8.4 DEK / KEK hierarchy

```
KEK (32-byte AES key, file-backed)
 └── wraps DEK (32-byte random per encryption)
      └── AES-256-GCM encrypts ConfigParts plaintext
```

- **KEK:** file `secrets/kek` (mode `0600`, gitignored); path override `FOCUSVPN_KEK_PATH`. Contents: raw 32 bytes **or** base64 of 32 bytes (match JWT seed file pattern from M1).
- **`kek_id`:** stable UTF-8 identifier for the KEK version (e.g. `kek-v1`) stored inside the envelope so rotation can select the right unwrap key.
- **DEK:** generated with `crypto/rand` per encrypt; never stored plaintext; only wrapped form in blob.
- **Signing key:** distinct Ed25519 seed/file via `FOCUSVPN_CONFIG_SIGNING_KEY_PATH` (default `secrets/config_signing_seed`); **must not** equal JWT Ed25519 material.

### 8.5 Envelope blob layout (`content_encrypted`)

Single `bytea` value, versioned binary layout (no new crypto — framing only):

| Offset / field | Size | Description |
|---|---|---|
| `magic` | 4 | ASCII `MVN1` |
| `format_version` | 1 | `0x01` |
| `kek_id_len` | 1 | length of kek_id |
| `kek_id` | N | UTF-8 |
| `wrap_nonce` | 12 | GCM nonce for DEK wrap |
| `wrapped_dek` | 32+16 | AES-256-GCM(KEK, wrap_nonce, DEK) = ciphertext\|\|tag |
| `data_nonce` | 12 | GCM nonce for content |
| `ciphertext` | variable | AES-256-GCM(DEK, data_nonce, parts_canonical) = ciphertext\|\|tag |

Nonces: 96-bit random from `crypto/rand`; never reuse (nonce, key) pair. AAD for both GCM ops: `magic || format_version || kek_id` (binds blob metadata).

### 8.6 `content_hash`

SHA-256 over the **canonical ConfigParts plaintext bytes** (same bytes fed to AES-GCM). Stored as 32 raw bytes in `content_hash`.

### 8.7 Signature verification (client)

1. Rebuild canonical `{config_version, parts}` from response.
2. Verify Ed25519 with CP **config** public key embedded in the client app.
3. Reject if signature invalid.
4. Reject if `config_version` &lt; locally cached version (rollback protection).
5. On HTTP `410 Gone`, invalidate cache.

### 8.8 Key rotation / rollback protection

| Key | Rotation |
|---|---|
| KEK | Introduce `kek-v2` file/id; new encrypts use v2; decrypt accepts v1+v2; rewrap lazy on read or batch job (scheduler later) |
| config_signing_key | Annual / on compromise; clients need new embedded pubkey (app update) or dual-verify window (Phase 3+) |
| Config version | Monotonic per allocation; never decrease; revoke → mark config revoked + issue higher version only when re-provisioning |

Rollback of a lower signed version is rejected client-side; CP never re-activates a lower version for the same allocation.

## 9. Database migration strategy (design — do not create yet)

New forward migration `000002_allocations_configs`:

- Create `vpn_allocations` and `vpn_configurations` exactly as [[DATABASE]] §2.7–§2.8.
- FKs: allocations → users/devices/endpoints; configurations → allocations/devices.
- Partial uniques as documented.
- `.down.sql` drops both tables in FK-safe order.

M2 tables unchanged. No speculative columns (DNS/MTU stay CP constants until needed).

ER clarification: one allocation has a **version lineage** of configurations (`UNIQUE(allocation_id, version)`); at most one `status=active` config per allocation (enforce in app or partial unique).

## 10. Authorization matrix

| Endpoint | Auth | Checks |
|---|---|---|
| GET /servers | Access JWT | User active; subscription gate §17-C |
| POST /connections | Access JWT | Device belongs to `sub`; device active; subscription; plan limits §17-B |
| DELETE /connections/:id | Access JWT | Allocation.user_id = principal |
| GET /configurations/:id | X-Device-Token | HMAC hash matches device; device owns config; config active |

Never return: password hashes, refresh/device token hashes, KEK, DEK, signing private key, envelope internals, peer private keys.

Leaked access token: can list servers / create connections for that user but **cannot** fetch ConfigParts without device token. Device token leak: can fetch that device’s configs only.

## 11. Failure handling

| Failure | Behavior |
|---|---|
| No HEALTHY endpoint / no pubkey (if required) | `503 node_unavailable` |
| IPAM exhausted | `503` or `409` (document as `node_unavailable` / capacity) |
| Unique IP race | Retry allocate |
| Crypto / KEK file missing | Startup fatal if configs module enabled (same no-silent-fallback spirit as postgres store) |
| Config revoked | `410 gone` |
| Bad / missing device token | `401 invalid_token` |
| Stale client cache | Client rejects lower version; must POST connections / refetch |

## 12. Concurrency and stale-version

- CP is source of truth for `version`.
- Concurrent POST connections: unique (device, endpoint) active prevents double-active; idempotent reuse preferred.
- Agent desired-state version (ADR-004) is M4; M3 may store allocation/config only.
- After revoke, GET old `config_id` → 410 even if client presents a previously valid signature blob from cache (client must honor 410).

## 13. Security analysis

| Threat | Mitigation |
|---|---|
| DB compromise | Envelope: attacker gets ciphertext + wrapped DEK; needs KEK file/KMS |
| Filesystem compromise (`secrets/`) | Treat as key compromise: rotate KEK + signing key; revoke sessions; 0600 + gitignore; prod → KMS |
| Config signing key compromise | Rotate key; clients update pubkey; re-sign or force re-provision |
| Configuration tampering (MITM/cache) | Ed25519 signature on canonical payload; TLS still required in prod |
| Replay old config | Monotonic `config_version`; client rejects downgrade |
| Rollback | Same as replay; revoked → 410 |
| Malicious admin | RBAC `admin`; audit later; M3 does not expand admin API |
| Leaked access JWT | Short TTL (15m); no config fetch without device token |
| Leaked device token | Scope limited to that device’s configs; revoke device |

## 17. Decisions (approved 11.08.2026)

**Ready for implementation: YES.** Code/migrations start only on explicit user “START M3”.

| ID | Decision | Notes |
|---|---|---|
| **A** | **A1** | DEV-ONLY AmneziaWG **server** public key in seed + endpoint HEALTHY for local/dev; allocation `pending→active` immediately under a **dev-only** path (prefer `FOCUSVPN_ALLOCATION_AUTO_ACTIVE` or equivalent). Stub is WG server pubkey identity for ConfigParts — **not** agent mTLS, **not** config signing. M4: agent-generated pubkey + confirm-before-`active` in non-dev. Private server keys never on CP. |
| **B** | **1 active+pending allocation per device** | `409 too_many_allocations` when exceeded; prefer idempotent reuse of existing pending/active. |
| **C** | **Implicit free entitlement** | No subscription row → free-plan entitlement (M2-consistent). Existing subscription not live (`expired`/`cancelled`) → **402**. Live `trialing\|active` → allow. |
| **D** | **Canonical sorted compact JSON + `MVN1` envelope** | Sign `{config_version,parts}` per §8.2; `content_encrypted` layout §8.5; primitives AES-256-GCM + Ed25519 + SHA-256 only. Freeze after implement; use `format_version` for future changes. |
| **E** | **No Redis in M3** | Desired-state notify = no-op until M4; compose Redis remains infra-prep. |
| **F** | **`connection.id` = `allocation.id`** | Same UUID; API name “connection”, DB table `vpn_allocations`. `config_id` = `vpn_configurations.id`. |
