# ADR-006: Модель сессий и refresh-токены

- **Статус:** Принято (PHASE 1, 10.08.2026)
- **Дата:** 10.08.2026
- **Основа:** `docs/SECURITY.md` §3; `docs/DATABASE.md` §3.1; `docs/API.md` §2

## Контекст

Нужна сессионная модель для мобильных/десктопных клиентов: без постоянных паролей, с отзывом
доступа, устойчивая к краже токенов.

## Решение

- **Access JWT** (15 мин, `sub`+`role`+`jti`), алгоритм **EdDSA (Ed25519)** — не HS256;
  **opaque refresh token** (256 bit) — только HMAC-хэш в БД, TTL 30 дней, со **скользящим продлением**.
- **Ротация при каждом refresh**: старый refresh инвалидируется (`revoked`, `replaced_by`).
  Повторное использование отозванного токена (reuse detection) → отзыв **всего семейства**
  (`family_id`) → принудительный re-login.
- Привязка сессии к `device_id`; logout отзывает семейство.
- Rate limiting на login/register (IP + аккаунт), задержки при брутфорсе (см. SECURITY.md §6).

## Последствия

**Плюсы:** малый риск долгоживущих токенов, быстрый отзыв, устойчивость к краже refresh.

**Минусы:** требуется синхронизация семейства (атомарность в БД), клиент должен корректно
обрабатывать 401 на refresh (re-login).

## Альтернативы

- Refresh без ротации (тот же токен) — отклонено: длинная жизнь токена при краже.
- Только long-lived JWT — отклонено: нет отзыва, утечка = полный доступ.
- OAuth/OIDC-провайдер — избыточно на старте; можно добавить позже поверх внутренней модели.
