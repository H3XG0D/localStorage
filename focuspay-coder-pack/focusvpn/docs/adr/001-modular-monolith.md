# ADR-001: Modular Monolith для Control Plane

- **Статус:** Принято (PHASE 1, 10.08.2026)
- **Дата:** 10.08.2026
- **Основа:** `docs/ARCHITECTURE.md` §4; `docs/DATABASE.md`

## Контекст

Control Plane должен обслуживать клиентов (5 платформ), ноды, админов; управлять подписками,
конфигурациями, аллокациями. Стандартный выбор — микросервисы. Однако команда малая, продукт
на старте, а границы доменов (auth, devices, nodes, allocations) тесно связаны транзакционно
(выдача конфигурации трогает devices + nodes + allocations + configurations).

## Решение

Строим **modular monolith**: один Go-процесс, внутри — логические модули с явными границами
(`backend/internal/{auth,users,devices,subscriptions,nodes,endpoints,allocations,configurations,
health,scheduler,admin}`), каждый со своим storage/интерфейсом. Модули общаются через внутренние
интерфейсы, не через HTTP между собой. Деплой — один артефакт + Postgres + Redis.

## Последствия

**Плюсы:** одна база данных (транзакции в пределах домена), один процесс для деплоя и логирования,
быстрая разработка, меньше инфраструктуры, отсутствие сетевых задержек между доменами.

**Минусы:** риск «плоского спагетти» — снимаем жёсткими границами модулей и тестами; масштабирование
только вертикально до определённого предела. Переход на микросервисы позже реален, т.к. границы
модулей уже намечены.

## Альтернативы

- Микросервисы (не выбрано: инфраструктурная сложность не окупается на старте).
- Единый «fat» сервис без модулей (не выбрано: нет границ для будущего разделения).
